# 常见错误（Bad → Good）

> 每条错误都来自真实使用场景。看懂了这里，你就知道每个模板为什么要那么写。

## 1. Agent 写得太全能

**Bad**

```text
你是一个全能的软件开发专家。
你需要分析需求、设计架构、写代码、测试、Review，
并确保最终任务完成。
```

**Good**

```text
你负责实现已经确认的技术方案。
你不负责修改产品需求，也不负责最终 Review。
```

为什么：全能 Agent 同时占用了 Agent / Squad / Skill / Issue 四个位置，换任务就全部失效；窄 Agent 可以原样复用到下一个任务。

## 2. Squad 只有一句空话

**Bad**

```text
大家协作完成任务，必要时互相帮助。
```

**Good**

```text
前端实现 → FrontendDev（范围含前端）
后端实现 + API 契约 → BackendDev（范围含后端）
判门 → Leader 用 multica-verification skill 复跑
业务评审 → Reviewer
测试 → Tester

判门 FAIL → 对应实现者
Test FAIL → 对应实现者
```

为什么：Squad 的价值就是**明确的路由**。路由模糊时，每个 Agent 都靠猜决定自己下一步做什么。

## 3. Issue 没有验收标准

**Bad**

```text
帮我把这个功能做了。
```

**Good**

```text
目标：...
范围：...
非目标：...
验收标准：- [ ] ...
约束：...
验证方式：...
```

为什么：没有可测试的验收标准，门禁体系（G0–G4）直接失效，Verification 无处判门。

## 4. 让完成者自证

**Bad**

```text
实现者写完代码后：请自己 Review 一遍，确认没问题后标记完成。
```

**Good**

```text
实现者写完代码后：提供证据（变更文件 + 命令输出），由 Leader 用 multica-verification skill 复跑判门。
```

为什么：作者会本能地为自己找理由。判门必须由非产出者执行（Leader 复跑或 CI），产出者自证不算数。

## 5. 把硬约束写进 Prompt

**Bad**

```text
Agent 必须确保代码没有任何安全问题，并且测试全部通过后才能提交。
```

**Good**

```text
用 CI 强制测试通过，用分支保护要求 PR 审批。Agent 指令只是引导。
```

为什么：LLM 指令不是安全边界。真正「必须」的规则要放在工程系统里强制执行。

## 6. 用「做完了」代替证据

**Bad**

```text
Squad Leader 判断任务完成的标准：成员报告完成。
```

**Good**

```text
Squad Leader 判断任务完成的标准：变更文件 + 实际命令输出 + 与验收标准逐条对照。
```

为什么：「完成」是口头声明，证据是可复现的事实。只信后者。

## 7. 无脑复制五 Agent 流程

**Bad**

```text
所有任务都走：Architect → Frontend/BackendDev → Tester → Leader 判门。
包括改一行配置、修一个 typo。
```

**Good**

```text
按任务类型选最小组合：Bug 用 bug-fix（跳过 Architect），
小改动可以只派 BackendDev + Reviewer，研究类任务甚至不需要开发角色。
```

为什么：最佳实践不是固定流程，而是**针对任务选最小可行组合**。流程越重，上下文损耗越大。

## 8. 让 Leader 亲自干活

**Bad**

```text
Leader 是万能兜底：其他人做不了的，Leader 自己上。
```

**Good**

```text
Leader 只做路由、门禁判断与升级。实现永远派给对应成员。
```

为什么：Leader 是指挥，哪有指挥亲自干活的。

---

## 诊断清单

如果你的小队「看起来在跑，但结果不稳定」，按顺序检查：

1. Issue 有没有可测试的验收标准？（没有 → 一切免谈）
2. 每个 Agent 是不是只干一件事？（有重叠 → 行为会漂移）
3. 判门是不是由非产出者执行？（作者自判 → 等于没查）
4. 完成标准是不是证据？（口头报告 → 无法复盘）
5. 硬约束在不在 CI / 分支保护里？（只在 Prompt 里 → 早晚被绕过）
