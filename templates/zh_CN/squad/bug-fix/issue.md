# Issue Template

> 复制到新 Issue，填写后交给 Squad。

```markdown
# Bug

## Issue 来源（必填，二选一）
- [ ] 外部系统链接（轻量）
      - 链接：https://jira.example.com/browse/<ISSUE-KEY>
      - 摘要：<!-- 一句话说明现象 -->
- [ ] 全量自包含（默认）：本 Issue 即为需求，完整填写以下章节

## 严重级别（必填）
- [ ] S0 — 阻断生产 / 数据安全 / 大范围不可用
- [ ] S1 — 核心功能严重受损，需要优先修复
- [ ] S2 — 一般功能问题，有明确影响但存在可接受绕行
- [ ] S3 — 低影响问题 / 边界体验问题

## 变更类型（必填）
- [ ] Bug Fix
- [ ] Regression
- [ ] Performance
- [ ] Security
- [ ] Data / Migration
- [ ] Other: <!-- 说明 -->

## 复现步骤
1.
2.
3.

## 期望行为
<!-- 应该发生什么 -->

## 实际行为
<!-- 实际发生了什么 -->

## 影响范围
- 影响端（勾选，缺失即不派角色）：
  - [ ] 前端
  - [ ] 后端
- 影响的用户 / 模块 / 版本：

## 根因假设
<!-- 如果已知，写在这里；未知时写「待确认」即可，不要猜 -->

## 修复要求
- [ ] 定位根因
- [ ] 最小范围修复
- [ ] 回归测试（或说明无法自动化的原因）

## 验收标准
- [ ] 按复现步骤不再出现该问题
- [ ] 既有行为不回归
- [ ]

## 参考资料
<!-- 日志、截图、错误信息、相关代码位置 -->
```

---

## 为什么这么写

Bug Issue 除了要可复现，还必须先表达 **Severity + Change Type**。Severity 决定升级与验证强度；Change Type 防止把安全、数据迁移、性能类风险伪装成普通 Bug Fix。

复现步骤 + 期望/实际行为三段写清，实现者才能不靠猜直接定位根因。根因未知时允许「待确认」，禁止编造。

## 常见失败

- **没有 Severity**：生产阻断和低优先级体验问题会走同一条路径。
- **没有 Change Type**：安全 / 数据 / 性能风险容易被普通修复流程掩盖。
- **只有一句话描述、没有复现步骤**：实现者只能靠猜改代码。
- **复现步骤缺环境条件**（版本、数据、登录态）：别人复现不出，门禁无法判 PASS。
- **用解决方案替代根因假设**：Issue 应记录问题事实与假设，不应提前规定补丁。
- **跳过回归验证**：修复没有回归证据，后续无法证明没有复发。
