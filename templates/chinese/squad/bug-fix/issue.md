# Issue Template

> 复制到新 Issue，填写后交给 Squad。

```markdown
# Bug

## 复现步骤
1.
2.
3.

## 期望行为
<!-- 应该发生什么 -->

## 实际行为
<!-- 实际发生了什么 -->

## 影响范围
- 影响端（勾选，缺失即不派角色）：
  - [ ] 前端
  - [ ] 后端
- 影响的用户 / 模块 / 版本：

## 根因假设
<!-- 如果已知，写在这里 -->

## 修复要求
- [ ] 定位根因
- [ ] 最小范围修复
- [ ] 回归测试（或说明无法自动化的原因）

## 验收标准
- [ ] 按复现步骤不再出现该问题
- [ ] 既有行为不回归
- [ ]

## 参考资料
<!-- 日志、截图、错误信息、相关代码位置 -->
```

---

## 为什么这么写

Bug Issue 的第一要务是「可复现」。复现步骤 + 期望/实际行为三段写清，实现者才能不靠猜直接定位根因。
